# github backend 开发经验

本文档记录 `backend/github` 一次交付（约 2100 行代码 + 真实凭证验收）过程中沉淀的教训，供后续新增 backend 前重读。核心事实是：逻辑单元测试从头到尾全绿，但九个真实缺陷全部在真实凭证验收阶段才暴露——单测覆盖不到协议约束、CDN 缓存、迭代顺序这类问题，验收才是照妖镜。

## 接口契约的真实来源是 fstests

本次约一半的 bug 源于对 rclone 接口语义的想当然：`Mkdir("")` 不是 no-op 而是"创建 Fs 根目录本身"（`rclone mkdir remote:dir` 实际以 dir 为 root 调用 `Mkdir("")`）；Move 不保证目标目录已存在，backend 需自建目录链；DirMove 要求目标已存在时返回 `fs.ErrorDirExists`；NewObject 必须返回有意义的 modtime（零时间无法通过 fstests 的精度检查）。这些语义在 `fstest/fstests/fstests.go` 里全都有明确断言。结论：写 backend 前先通读相关测试段，接口契约以测试代码为准，而非接口注释或直觉。

## rclone encoder 的隐藏双向语义

encoder 的转换不是单向的：`FromStandardName = e.Encode(Standard.Decode(s))`，`ToStandardName = Standard.Encode(e.Decode(s))`。Standard 层会无条件做字符替换（如孤立 `.`/`..` 表示为全角点），backend 的 flags 只控制额外的百分号编码。因此编码集漏掉 `EncodeDot` 时，标准名里的全角点会在 FromStandard 阶段被还原成 ASCII `.`——对 git 这类禁止 `.`/`..` 路径组件的系统是非法路径。选编码集之前先读 `lib/encoder/encoder.go` 的实际转换链，不要假设 flags 描述了全部行为。

## 参考实现要理解后重写，不能移植语义

OpenList 的 github 驱动自身存在三个缺陷：嵌套路径场景下公共祖先计算会数组越界 panic；non-fast-forward 时用旧 tree 重提交会静默覆盖外部并发提交；raw 下载 URL 有写后读旧内容问题。最初照搬其三段式路径分析，继承了同样的风险；后来放弃移植，改为"变更集合自底向上重建"（`applyEdits`）的通用算法，反而覆盖了参考实现 panic 的场景。参考代码的价值是告诉你协议怎么用，不是告诉你架构怎么设计——尤其当参考实现自身没有被严格测试覆盖时。

## 依赖迭代顺序的逻辑必须显式定序

`applyEdits` 曾有一个约 50% 概率失败的 bug：算法按"最深目录优先"处理变更，但同深度时依赖 Go map 的随机迭代顺序，根目录的编辑可能先于同深度的顶层目录变更被处理并提前 return，静默丢弃未应用的变更。第一次目录移动碰巧顺序正确，移动回来时碰错——单次验证根本暴露不了。教训：凡存在"处理顺序影响正确性"的环节，必须显式规定顺序（本例改为根目录永远最后处理），不能把正确性寄托在容器的偶然行为上。

## 可变路径加 CDN 缓存等于写后读不一致

raw.githubusercontent.com 按分支路径缓存内容，写后立即读会返回旧数据，且 query 参数绕不过缓存。解法不是绕缓存，而是换 URL 语义：用分支头 commit sha 锁定的路径内容不可变、天然免缓存（头 sha 带 TTL 缓存、本进程提交后立即刷新）。这个思路通用于一切"可变标识 + 中间缓存"的系统：读路径尽量锚定不可变版本。

## 协议行为用 curl 直测隔离

本次靠 curl 直测确认了多个协议事实：trees API 的 content 条目必须完全省略 sha 字段、删除条目必须显式 `"sha": null`（两者同时出现会被 422 拒绝）；空 tree sha 在仓库对象库中不存在时无效；CDN 缓存的触发条件是"先读→写→再读"（只测写后读复现不了）。隔离变量做最小实验，比在代码里边猜边改快一个量级。结论已固化进 `AGENTS.override.md` 的测试策略：协议存疑先 curl，拿到结论再写代码。

## 配额是测试预算

fstests 完整套件单轮约消耗 2000 次核心 REST 请求，连续三轮就把 5000/hr 的配额打爆，第四轮在测试初始化阶段即 403。API 型 backend 的验收要先估算配额账，把完整验收控制在单个限流窗口内；多轮调试时注意配额余量，必要时错峰。

## 计划偏离要记录

原实施计划按 M1-M4 分阶段交付，实际执行时发现 Fs 接口无法"部分编译"，拆阶段反而制造中间态缺陷，最终整体实现、统一验证，并把这次偏差与原因记入了实施计划文档。计划是活的：偏离时把原因写下来，比硬守计划更有价值——后续读者需要知道的是当时的权衡，而不只是结果。
