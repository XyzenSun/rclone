# github backend 开发经验

本文档记录 `backend/github` 一次交付（约 2100 行代码 + 真实凭证验收）过程中沉淀的教训，供后续新增 backend 前重读。核心事实是：逻辑单元测试从头到尾全绿，但九个真实缺陷全部在真实凭证验收阶段才暴露——单测覆盖不到协议约束、CDN 缓存、迭代顺序这类问题，验收才是照妖镜。

## 接口契约的真实来源是 fstests

本次约一半的 bug 源于对 rclone 接口语义的想当然：`Mkdir("")` 不是 no-op 而是"创建 Fs 根目录本身"（`rclone mkdir remote:dir` 实际以 dir 为 root 调用 `Mkdir("")`）；Move 不保证目标目录已存在，backend 需自建目录链；DirMove 要求目标已存在时返回 `fs.ErrorDirExists`；NewObject 必须返回有意义的 modtime（零时间无法通过 fstests 的精度检查）。这些语义在 `fstest/fstests/fstests.go` 里全都有明确断言。结论：写 backend 前先通读相关测试段，接口契约以测试代码为准，而非接口注释或直觉。

## rclone encoder 的隐藏双向语义

encoder 的转换不是单向的：`FromStandardName = e.Encode(Standard.Decode(s))`，`ToStandardName = Standard.Encode(e.Decode(s))`。Standard 层会无条件做字符替换（如孤立 `.`/`..` 表示为全角点），backend 的 flags 只控制额外的百分号编码。因此编码集漏掉 `EncodeDot` 时，标准名里的全角点会在 FromStandard 阶段被还原成 ASCII `.`——对 git 这类禁止 `.`/`..` 路径组件的系统是非法路径。选编码集之前先读 `lib/encoder/encoder.go` 的实际转换链，不要假设 flags 描述了全部行为。

## 参考实现要理解后重写，不能移植语义

OpenList 的 github 驱动自身存在三个缺陷：嵌套路径场景下公共祖先计算会数组越界 panic；non-fast-forward 时用旧 tree 重提交会静默覆盖外部并发提交；raw 下载 URL 有写后读旧内容问题。最初照搬其三段式路径分析，继承了同样的风险；后来放弃移植，改为"变更集合自底向上重建"（`applyEdits`）的通用算法，反而覆盖了参考实现 panic 的场景。参考代码的价值是告诉你协议怎么用，不是告诉你架构怎么设计——尤其当参考实现自身没有被严格测试覆盖时。

## 依赖迭代顺序的逻辑必须显式定序

`applyEdits` 曾有一个约 50% 概率失败的 bug：算法按"最深目录优先"处理变更，但同深度时依赖 Go map 的随机迭代顺序，根目录的编辑可能先于同深度的顶层目录变更被处理并提前 return，静默丢弃未应用的变更。第一次目录移动碰巧顺序正确，移动回来时碰错——单次验证根本暴露不了。教训：凡存在"处理顺序影响正确性"的环节，必须显式规定顺序（本例改为根目录永远最后处理），不能把正确性寄托在容器的偶然行为上。

## 可变路径加 CDN 缓存等于写后读不一致

raw.githubusercontent.com 按分支路径缓存内容，写后立即读会返回旧数据，且 query 参数绕不过缓存。解法不是绕缓存，而是换 URL 语义：用分支头 commit sha 锁定的路径内容不可变、天然免缓存（头 sha 带 TTL 缓存、本进程提交后立即刷新）。这个思路通用于一切"可变标识 + 中间缓存"的系统：读路径尽量锚定不可变版本。

## 协议行为用 curl 直测隔离

本次靠 curl 直测确认了多个协议事实：trees API 的 content 条目必须完全省略 sha 字段、删除条目必须显式 `"sha": null`（两者同时出现会被 422 拒绝）；空 tree sha 在仓库对象库中不存在时无效；CDN 缓存的触发条件是"先读→写→再读"（只测写后读复现不了）。隔离变量做最小实验，比在代码里边猜边改快一个量级。结论已固化进 `AGENTS.override.md` 的测试策略：协议存疑先 curl，拿到结论再写代码。

## 配额是测试预算

fstests 完整套件单轮约消耗 2000 次核心 REST 请求，连续三轮就把 5000/hr 的配额打爆，第四轮在测试初始化阶段即 403。API 型 backend 的验收要先估算配额账，把完整验收控制在单个限流窗口内；多轮调试时注意配额余量，必要时错峰。

## 计划偏离要记录

原实施计划按 M1-M4 分阶段交付，实际执行时发现 Fs 接口无法"部分编译"，拆阶段反而制造中间态缺陷，最终整体实现、统一验证，并把这次偏差与原因记入了实施计划文档。计划是活的：偏离时把原因写下来，比硬守计划更有价值——后续读者需要知道的是当时的权衡，而不只是结果。

# baidupcs backend 开发经验

本文档记录 `backend/baidupcs` 交付（真实凭据验收）过程中沉淀的教训。本次最刺眼的事实是：上一节记录的 encoder 全角点教训原样重犯，只是后果从"非法路径"升级为"目录被文件替换"——经验文档的价值取决于它在什么时机被阅读。

## 经验文档要在动手前重读，不是事后对照

选 baidupcs 默认编码集时没有回头读本文档，漏掉 EncodeDot；path.Join 的 Clean 会把 Standard 层解码出的 ASCII `.` 段直接消掉，create 于是落在父目录路径上，服务端用一个 100 字节文件替换掉了整个目录（fstests 的 dot_dot 用例触发，测试目录被毁）。EncodeSlash 同理：全角斜杠解码成 `/` 后路径分裂。教训的教训：新增 backend 的第一步应当是重读本文档并 `grep -rn 踩坑 backend/` 扫一遍既有实现的注释，把历史教训变成动手前的检查清单；"供后续新增 backend 前重读"只写在标题里等于没有。

## 副作用型"成功"比报错更危险

百度 create 对已存在路径不返回 -8，而是返回 errno 0 并在同一父目录额外创建一个空的 `{name}_{timestamp}` 副本；逐段盲建目录让用户网盘根目录累积了 35 个垃圾目录，调用方全程看到的是成功。判断远端 API 的错误语义时，除了测"失败返回什么"，必须测"重复调用、冲突调用是否静默产生服务端副作用"。防御模式：一切"创建"类操作先探测存在性，只对确认缺失的目标调用创建（本例为向上找最深存在前缀、只建缺失段）。协议实验尽量在 `/apps/{appname}` 应用沙箱里做，副作用不污染用户可见空间。

## fstests 是破坏性测试，也是误导源

fstests 会主动探测危险路径（dot/dot_dot、RootCollapse），必须在一次性随机子目录里跑，永远不要指向真实数据。同样重要的是定位纪律：目录树被毁后，十几个编码用例全部以 errno -7 失败，最初被误判为"百度拒绝这类名字"，差点据此给编码集加一堆不必要的 flag；curl 实测名字接受矩阵（前导空格/波浪号/各类符号/全角字符全部接受）后才纠正——那批 -7 全是连带伤害。批量失败时先修第一个失败并怀疑状态污染，逐个独立分析会得出错误结论。

## 事故现场用服务端 ctime 对账重建

目录被替换后没有本地日志可用，靠两条线索还原了完整机制：把每个 `WordAgent_时间戳` 垃圾目录的时间戳与操作时间线对账，确认"每次 create 已存在路径产生一个副本"；再用 filemetas 查那个 100 字节文件的 ctime，对上 fstests 用例的执行窗口与 `random.String(100)` 的内容特征，锁定肇事用例。远端对象的时间戳就是操作日志——排查先收集所有异常对象的 ctime/mtime 再对时间线，比读代码猜快一个量级。

## 运行期配置回写必须走 NewFs 传入的 configmap

环境变量覆盖选项时，fs.NewFs 会把 configName 改写成带 `{hash}` 后缀的缓存名，f.name 已不是真实配置段名；用 `fs.ConfigFileSet(f.name, ...)` 回写 token 会创建错误配置段（本次产生 `[testbd{51WZi}]` 残留段，真实段的 refresh_token 已被轮换消费变成失效值，需手工修复配置）。正确通道是 NewFs 收到的 configmap——它的 setter 在改名之前就已绑定真实段。任何运行期持久化 token 的 backend 都适用。

## 计划里的参考实现假设要动手前廉价证伪

计划假设"秒传可用"（来自 OpenList 驱动），实际该应用下官方客户端内容、开放平台内容、全零常见内容三种来源的 precreate 全部 return_type=1，create 式秒传恒返 31500；按假设实现的秒传尝试让每次上传白耗一次注定失败的调用。参考实现的行为不保证在你的应用/账号上成立——计划中标注"参考来源"的假设，实现前先用 curl 一分钟证伪；证伪后要么删掉死路径，要么留零成本分支（本例保留 precreate return_type=2 检查，将来放开即自动生效）。

## 多时间戳字段要实测哪个"活"过操作

百度同时返回 server_mtime 与 local_mtime：官方客户端上传时前者是上传时间、后者是真实修改时间；filemanager move 会重置前者、保留后者。fileModTime 最初按"server_ 前缀更权威"的直觉取值，导致 move 后 rclone 判等失效。字段多的 API 不要按命名直觉选权威字段——把"上传/移动/覆盖"三个操作各做一次，看哪个字段与源文件时间一致。

## 写后读的秒级旧值是服务端常态

覆盖上传后立即下载会拿到旧内容（秒级传播延迟），服务端 Copy 后立即 list 也可能找不到新文件；这不是可修的 bug，是必须容忍的语义。设计上：读路径带重试（Copy 的定位重试、验收时隔几秒复测），不要把写后立即读的旧值当成代码缺陷去排查。
